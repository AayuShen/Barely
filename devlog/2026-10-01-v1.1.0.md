# Devlog: 2026-10-01, v1.1.0 (update log)

*Barely, by AayuShen*

## Goals for this update

v1.0.0 proved the idea. v1.1.0 makes it trustworthy and useful day to day:

1. Stop reporting success when nothing actually changed.
2. Survive Explorer restarts without a background process.
3. Add the styling options people ask for: tint, border, maximized, light mode.
4. Ship properly: tests, CI, security scanning, releases with checksums.

## The bug that shaped this release

While testing v1.1, `barely --diagnose` timed out. A trace log from inside Explorer showed
the DLL reading Barely's settings key as **not found** (error 2), even though the values
were right there in `regedit`.

The cause: the tool I was testing from runs child processes in a sandbox that gives them
their own private overlay of the registry. Barely saved settings into that overlay;
Explorer, outside the sandbox, never saw them. Worse, **v1.0.0 couldn't notice**. It reported
"Taskbar opacity set to 0%" as soon as the DLL loaded, so the v1.0 devlog's "tested"
entry was really only "the DLL loaded". The taskbar itself may never have changed during
those tests.

That's the reason for the two-way handshake in v1.1:

- The DLL publishes how many taskbar elements it styles (`Runtime\Targets`) and its version.
- Every apply writes a fresh `Stamp`, and the DLL echoes back the stamp it actually read
  (`Runtime\StampSeen`).

So `barely` now reports exactly one of these: it worked; the taskbar layout wasn't recognized
(run `--diagnose`); an older DLL is loaded (restart Explorer); or settings aren't reaching
Explorer (run from a normal terminal). The trace showed the DLL was finding the taskbar
all along: **2 elements**, the background and the border.

## Design notes

- **Auto-repair without a resident process.** Windows has no "Explorer started" event that a
  normal user can subscribe to, and staying resident to listen for `TaskbarCreated` would
  break Barely's promise. A scheduled task that starts `barelyw.exe --ensure` once a minute
  costs a few milliseconds per run: it checks Explorer's module list and exits.
- **Maximized mode** uses WinEvent hooks running on the DLL's existing control thread, so
  there's no new thread. The location-change hook is scoped to the foreground window's process
  and re-scoped on every foreground change, so the mouse-move noise from the rest of the
  system never reaches Explorer.
- **Light mode** watches `SystemUsesLightTheme` with the same registry-notification
  mechanism as the settings, so there's still no polling.
- **Tint** replaces the background rectangle's `Fill` with a `SolidColorBrush`. A
  property-changed callback restores it if Windows swaps the theme brush back in.
- **Settings window** is plain Win32 with common controls v6, about 200 lines and no
  framework. Every slider move is a registry write, and the DLL applies it live.

## Deferred (and why)

- **Per-monitor settings:** the system XAML used by the taskbar doesn't expose which
  window or monitor an element belongs to. That needs more research to do safely.
- **Code signing:** requires a certificate in AayuShen's name (for example Azure Trusted
  Signing).
- **winget package:** needs a pull request to `microsoft/winget-pkgs` from AayuShen's account.
- **Antivirus submissions:** have to be filed by the publisher.
- **Screenshot in README:** needs a capture of a real desktop.

## Verification

  missing DLLs (with no settings touched), ASLR/DEP/CFG on all binaries, and version
  metadata.
- MSVC `/analyze`: **0 warnings**, after fixing 5 (null-termination proofs, SAL annotations
  on the COM exports, a possibly-null module handle, and `GetTickCount64`).
