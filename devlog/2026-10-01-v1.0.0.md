# Devlog: 2026-10-01, v1.0.0

*Barely, by AayuShen*

## Goal

Make the Windows 11 taskbar transparent permanently, **without a program running all
the time** and using memory. Tools like TranslucentTB stay resident because the
transparency they set gets reset by Explorer.

## Approaches considered

1. **Settings → Transparency effects.** Built in, but only a light acrylic tint.
2. **`TaskbarAcrylicOpacity` registry value.** Worked on Windows 10 and early
   Windows 11, and is ignored on current builds.
3. **`SetWindowCompositionAttribute` on `Shell_TrayWnd`.** Explorer resets it when you
   open Start, maximize a window or change the theme, so it needs a resident process to
   keep reapplying it. Rejected.
4. **Edit the taskbar's XAML via `InitializeXamlDiagnosticsEx`.** Chosen. The Windows 11
   taskbar background is a XAML `Rectangle` (`BackgroundFill`). Setting its `Opacity`
   from inside Explorer persists through Start, maximized windows and app switches,
   because Explorer itself is now drawing it transparent.

## Design

- **`barely.exe`** runs for about a second and exits: it saves the setting, verifies,
  injects and confirms.
- **`barely_tap.dll`** lives inside Explorer. It watches the visual tree for the
  background rectangles, sets `Opacity`, and uses a property-changed callback to undo
  any reset.
- **Live updates:** the DLL waits on a registry change notification, so changing the
  opacity is just a registry write, with no second injection and no polling.
- **`barelyw.exe`:** the same source built with the Windows subsystem, used for logon
  autostart so no console window flashes.

## Security pass

Because the DLL runs inside the shell, v1.0.0 adds a set of protections: a build-time
SHA-256 pin of the DLL with the file locked until it's loaded, verification that the
target is the real `explorer.exe`, a host check inside the DLL, no elevation, System32-only
DLL search, a quoted Run path, and a hardened compiler/linker configuration. See
`SECURITY.md`.

## Toolchain notes

- MSVC 14.51 (VS Build Tools 2026) installed to `E:\DevTools\VSBuildTools`.
- The Windows SDK installer would only install to C: because an earlier partial install
  had fixed its location, so the SDK was unpacked from Microsoft's `Microsoft.Windows.SDK.CPP`
  NuGet packages into `E:\Libs\WindowsSDK\10` instead. `INCLUDE`, `LIB` and `PATH`
  are set as user environment variables, and `build.cmd` uses them when present.

## Tested

- `barely --version`, argument validation (`101` rejected).
- Tampered DLL (one byte flipped): refused to load.
- `barely 0`: DLL loaded into Explorer and the taskbar was set to 0%.

> **Correction (v1.1.0):** "set to 0%" was only what v1.0 *reported*. The tests ran from a
> sandbox with a private registry overlay, so Explorer never received the setting, and v1.0
> had no way to notice. See the v1.1.0 devlog for how this was found and fixed.
